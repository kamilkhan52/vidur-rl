## Findings

### [major] M3: the pre-registered fail reading uses a 50 % precision bar, which noise overrides already reach, and ignores the size of gains and losses
`headroom.py:274-278`.

**Why 50 % is the noise level.** The audit scores each candidate on **one** true future. That future is a draw from (approximately) the same distribution the K sampled futures come from, independent of them.
- Take an override chosen on noise, i.e. a near-tie whose expected gain μ ≈ 0. Its single-future true gain is about N(0, σ), so it is "right" (true gain > 0) about **50 %** of the time, whatever the selection.
- Take a genuine override that just clears the bar (μ ≈ 1.15σ at K = 8). It is right with probability Φ(1.15) ≈ 0.87.

So 50 % is not the boundary between "mostly wrong" and "right". It is what pure noise gives. "Precision >= 50 %: right overrides, too few or too small" would read a noise-only B2 as a success of the rule.

**Second problem: precision ignores magnitude.** 60 % small wins with 40 % large losses is a net harm that a P99 objective punishes, and it still has precision 60 %.

**Failure scenario.** B2 fails the gate. The audit shows 55 % precision because most overrides were near-tie noise. The pre-registered reading then says "right overrides, too few or too small to move the P99" and points step C toward more K or a better length predictor, when the evidence says the rule is overriding on noise.

**Fix** (text, before any B2 log is read; the logs already hold everything needed):
1. **Primary audit statistic:** the mean true gain per override, `score_true[pe] - score_true[chosen]`, pooled over the 4 windows, with a 95 % bootstrap CI (resample decisions within each window). Read a fail as:
   - "overrides wrong" if the CI is entirely ≤ 0;
   - "right but too few or too small" if the CI is > 0;
   - otherwise "inconclusive".
2. **Calibration instead of a fixed 50 %:** compare realised precision with what the model predicts for those same overrides. Under the model, an override is right with probability P(true gain > 0) ≈ Φ(mean d / sd d), using each override's logged `score_k`. Realised ≪ predicted means the length model is biased; realised ≈ predicted means the rule is calibrated.
3. **Baselines from the same logs.** `score_true` is logged for every candidate, so any rule can be scored on the same decisions: B's mean rule at K = 8 (argmin of `score`), a uniformly random alternative, and lcb. B2's overrides should beat the mean rule's picks on mean true gain.
4. **Fix the details now:**
   - Ties count as not right.
   - Pool over windows, and report per window as well.
   - With fewer than ~30 overrides pooled, the reading is "underpowered".
   - Optionally add `audit_stats(log_path)` now and put it in `gate_sha`'s list, so the reading is code before data. That is not required; the text alone fixes it.

### [minor] 1: the skew check pooled the alternatives the rule can never pick
Docstring `headroom.py:268-273`. "All decisions x 7 alternatives" is dominated by alternatives with a clearly negative mean d, which the rule never takes. The rare-loss pattern matters only among alternatives with a positive mean d (or each decision's top LCB). In that subset the excess over normal (2.1-2.8 % vs 2.1 %) could be larger than the pooled figure suggests.

**Fix:** none is needed to launch, because the audit measures the realised result. If the numbers are rerun, restrict to mean d > 0 and quote that figure.

### [minor] 2: the audit adds a fifth wave per decision: about +25 % wall time, not +12.5 %
`headroom.py:1124-1126`, `:883-887`, docstring `:284-286`. `_run_children` runs synchronous batches of `workers`, so the 64 sampled rollouts take 4 full waves of 16. The audit's 8 rollouts are a separate call: a fifth wave, half empty, that waits on its slowest child. CPU cost is +12.5 %, as stated, but wall time per decision is about 5/4 of the unaudited run. Each wave ends at its slowest of 16 children.

The "~15-20 h per window" is probably still within the 10 x 4 h chain. Treat it as optimistic.

**Fix (optional, before launch only; it changes `closed_crn`'s sha):** submit the audit children in the same `_run_children` call as the sampled ones. Or state ~18-25 h. With `--workers 18`, 72 rollouts would take exactly 4 waves, and memory allows it.

### [minor] 3: the gate does not record or require the audit
`headroom.py:1969-1972`. The pre-registered fail reading depends on `audit_true`, but `gate_verdict` neither reports it per window nor checks it. If one chain had been launched without `--audit-true`, nothing would say so until the analysis. That is unlikely, since the runbook has it.

**Fix:** add `"audit_true": p.get("audit_true", False)` to `per[tag]` (`gate_sha` only), or have M3's `audit_stats` refuse un-audited logs.

### [nit] 1: stale CPU note
`headroom.py:184` and `:197` still say "acpu, <= 22 CPUs" and "Two such chains at once stay within 22 CPUs". This contradicts the measured QoS (no per-user cap) that the B2 sizing relies on. Update the pilot paragraph or mark it historical.

### [nit] 2: one audited decision is checked independently
The test checks `score_true` independently only for the first planned decision, before any override has changed the parent's state. Later audits share the code path, so this is acceptable. Asserting `score_true` is present on every row would cost nothing.
