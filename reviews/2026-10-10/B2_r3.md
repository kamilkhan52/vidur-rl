## Findings

### [minor] 1: merging the audit into one batch does not cut the waves at `--workers 16`
`headroom.py:1043-1053`, `:889-893`, runbook `:299`, cost `:290-292`. `_run_children` takes fixed batches of `workers`, so 72 children run as 16+16+16+16+8: still 5 synchronous waves, the same as r2's separate call. Wall time per decision is therefore still about 5/4 of the unaudited run. The "~15-20 h per window" still assumes 4 waves.

**Fix (pick one before launch; neither changes results):**
- Use `--workers 18` with `--cpus-per-task=24`. 72/18 gives exactly 4 waves, and memory is ample at about 5 GB per 8 workers.
- Or state ~18-25 h per window. The 10 x 4 h chain covers either.

### [minor] 2: "predicted precision" is not a calibration check, because it is at least 0.874 by construction
`headroom.py:2024-2027`, `:2041-2044`, docstring `:277-279`. An lcb override has LCB > 0, so mean d / sd d > t_crit/√K = 3.238/√8 = 1.145, and its Φ(mean d / sd d) > 0.874. The 8 futures that selected it also estimate it, so it is inflated by selection.
- Under pure-noise overrides, realised precision is about 0.5 against a predicted ≥ 0.87.
- Under real overrides with an *unbiased* length model, realised precision is still below predicted, because of regression to the mean.

So "realised < predicted" cannot separate a biased model from selection noise. I suggested this comparison in r2; it was wrong. The pre-registered reading does not depend on it, but `audit_stats`' docstring says precision "is read against this prediction".

**Fix:** label `predicted_precision` as an upper bound inflated by selection (≥ Φ(t_crit/√K)) and drop "read against this prediction". If a model-bias check is wanted, compute calibration over **all** decision x alternative pairs, unselected: bin Φ(mean d / sd d) and compare with the realised [g > 0]. The logs already hold everything. Optional.

### [minor] 3: a CI that straddles 0 is read as "not better", which over-reads a low-power result
Docstring `:281-283`. With ~30-60 overrides and a single true future per override (paired SD ~1,000 units), the CI half-width can be several hundred units. The rule's bar alone means μ ≥ ~1,150, but a real gain of a few hundred would also straddle 0.

**Fix (text):** three readings.
- CI entirely ≤ 0: not better.
- CI > 0: right but insufficient.
- CI straddles 0: inconclusive, quoting the CI's upper end as the largest per-override gain the data allow.

### [minor] 4: the audit's CI is i.i.d. over overrides that share each window's one true future
`headroom.py:2059`. The module uses a moving-block bootstrap (`BLOCK = 20`, review G r4) for open-loop points for this reason: neighbouring points share futures. Overrides in one window see the same true arrivals and lengths, and nearby ones the same upcoming burst. So g can be positively correlated, and an i.i.d. CI too narrow. Overrides are sparse, which weakens this, but the pre-registration should not depend on it.

**Fix:** use a window-stratified bootstrap with blocks in decision order, e.g. `boot_ci(..., block=...)` per window and combined. At minimum, report `lag1` of g in decision order per window next to the CI.

### [minor] 5: `audit_logs` does not tie the log to the gated B2 row or check that it is complete
`headroom.py:2070-2083`. It takes any `closed_*.jsonl` in the directory whose header has `audit_true`. It does not check the rule, alpha, K, the current `decision_sha`, or that the log covers the whole window. The test itself audits a `max_decisions=2` log. A chain still in progress, or a stale audited log from earlier code, would be analysed silently. Only "2 audited logs" is refused.

**Fix:**
- Load the summary and find the head with `b_head_rows(rows, decision_sha("closed_crn"), 8, rule="lcb")`.
- Read `out/f"{_row_key(head['params'])}.jsonl"`.
- Require len(rows) == the head's `planned`, and require `params["audit_true"]`.
- Record an `audit_sha` (the source of `audit_stats` and `audit_logs`) in the output, as `gate_sha` does.

### [nit] 1: "the same decisions" in the docstring describes the baselines loosely
`headroom.py:2029-2031`. The baselines run on the same trajectory and true futures, but on different decision sets. The mean rule is scored at its own would-be overrides, and the random alternative over all decisions. A matched baseline answers "did the rule pick the right alternative where it acted": a random alternative at the lcb override decisions only. Add it, or say "same trajectory".

### [nit] 2: the mean-rule baseline's tolerance differs from `select_candidate`'s
`headroom.py:2049-2050`. The baseline scales the tolerance by `abs(score)`; `select_candidate` uses the summed E2E (`parts["mean"]`) for the tail score. The difference is 1e-9 relative, so it is immaterial.
