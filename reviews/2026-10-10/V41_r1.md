### 1. Leak closure (62b5ea5)
Router-visible paths enumerated (grep of `block_hash_ids`, `num_decode_tokens`, `original_num_decode`, `total_tokens`,
`prefix_hashes` over `vidur/scheduler/global_scheduler/`, `evolve/`, `scripts/`):
- `RequestView` (evolved scheduler, `schedule()`): `prefix_hashes`, `inflight_prefix_tokens` and `active_prefix_tokens`

- Router-owned ledgers `_inflight`/`_active` (`_assign`) hold prompt hashes only. The new test checks this (every id
  < 10,000).
- `_cached_prefix_tokens`: the probe uses prompt hashes and is still capped at `num_prefill_tokens // block_size`.
  The built-in baselines' `get_cached_prefill_length` → `probe_cached_prefill_tokens` → `get_computed_blocks` caps at
  the prefill range and returns only a token count.
- `ReplicaView`: `kv_usage` cannot leak a request's total length up front, because `allocate_slots` is incremental
  (`num_new_tokens` per step).
- `RequestOutcome` at `first_token`: `completed_at=None`, `num_decode_tokens=None`, `num_cached_tokens` is the prefill

- `PolicyContext` carries rng, num_replicas, now and state. No simulator objects reach a policy.
- LEARNED (`learned_global_scheduler.py`): builds its own `RequestView` without hashes or ledger fields. `Outcome`
  (with `num_decode_tokens`) is built only in `on_request_end`. The teacher sees the same hash-free view. All six
  `evolve/rl_designs/*` and the three `rl_*` finalists read only views and outcomes.
- System and tunable baselines (SGLang, AIBrix, Mooncake, Dynamo) use `prefix_hashes` only through a leading-match
  count. That count was already bounded by the prompt, because output-position ids are unique to their row. So v4.1
  changes no result, which agrees with the golden identity. No policy, finalist, probe or design reads
  `len(prefix_hashes)`.
- No file under `evolve/{finalists,policies,rl_designs,probes,golden/policies}` imports `vidur`, `gc`, `inspect` or
  `sys.modules`, or walks frames (see minor #3).

`prompt_block_hashes` boundary behaviour (verified by repro):
- v4 prompt not a multiple of the block size (93-94 % of rows in all three v4 traces): it returns `p // 16` ids. The
  converter (`expand_block_hashes_unpadded`) puts exactly those prompt ids first, then row-unique ids for the partial
  last block and the output.
- v3 padded traces: `num_prefill_tokens` is padded to whole 16-token blocks, so `p // 16` equals the number of
  prompt-side ids (padding included) and the cut lands exactly at the decode ids.
- An exact multiple (64/16) gives 4 ids. A prompt shorter than one block gives `()`. A request without hashes gives
  `()`. After `restart()` it still uses the original prompt length.
- `Request.__init__` asserts `len(ids) == (p + d) // bs`, and the simulator validates trace block size == cache block
  size, so the fallback to `request.block_size` is safe (but see nit #4 on float block sizes).
- The new tests were checked against the old behaviour: with `prompt_block_hashes` monkeypatched back to the full list
  in both modules, `test_identical_prompts_..._router_views` and `test_state_tracker_uses_prompt_hashes_only` both
  fail (`assert 5 == 64 // 16`; shadow hit ratio 0.8 instead of 1.0). They test their claim.

## Findings

### [minor] sim_fork forcing wrapper breaks on observe() while an override is pending (merge interaction)
`evolve/sim_fork.py:805` (`_forcing_call(self, fn, *args)`) vs
`vidur/scheduler/global_scheduler/evolved_global_scheduler.py:384` (`self._call(observe, outcome, observe=True)`, added
by 559218e).

**Failure scenario:** sim_fork (main side) installs `_forcing_call` as the instance's `_call`. The A fixes (branch
side) made `_observe` pass `observe=True`. If an override is pending when an observe event fires, the call raises
`TypeError`. This happens when `override_next_decision` is called on a handle that is not at a decision (nothing
checks that), with a policy that defines `observe()`. Even with the kwarg accepted, the pass-through at line 809 would
count observe calls as `policy_calls`.

**Evidence (repro):** Conv 4R s1.5 w6000+300 p0, a 5-line policy with `observe`:
`run_to_decision(5)`, then stop at a non-decision event, then `override_next_decision(h, None)`, then
`next_decision()` → `TypeError _forcing_call() got an unexpected keyword argument 'observe'`.

**Impact:** current callers are unaffected. `headroom.apply_decision` and the sim_fork tests install overrides at a
decision, and the next event is then the GlobalScheduleEvent, so no observe can fire in between. The failure is loud,
not silent.

**Fix:** `def _forcing_call(self, fn, *args, **kw)` and pass `**kw` through on both `type(self)._call` calls, or
refuse in `override_next_decision` unless `h.at_decision()`.

**Hashed file:** no (`evolve/sim_fork.py`).

### [minor] RL_CACHE_AWARE state uses true output lengths in three feature groups, not two
`vidur/scheduler/global_scheduler/state_tracker.py:249-267` (`_extract_request_features`, used for the current
request at :203 and for each lookahead request at :309) and `:461`
(`_pending_decodes[replica] += request.num_decode_tokens`).

**Failure scenario:** any RL_CACHE_AWARE training or evaluation conditions on the true output lengths of the current
request, of the next K-1 queued requests, and of every request in flight on each replica.

**Evidence (repro):** two trackers, identical except that every request's decode length is 16 vs 600. Features that
differ: `req_decode_norm`, `req_decode_log`, `req_prefill_decode_ratio`, `replica0_pending_decode_norm`,
`replica0_pending_decode_log`, `lookahead0_decode_norm`, `lookahead0_decode_log` and
`lookahead0_prefill_decode_ratio`. The fixer's report missed `replica*_pending_decode_*`.

**Impact:** nothing current can select it (section 5), so this does not block the merge. Any historical RL_CACHE_AWARE
numbers (the EXP01-09 / graduation era) were produced by an oracle-informed router and must not be presented as
deployable RL results.

**Fix (cheap):** make `StateTracker` refuse to build, or zero those 3 + 2M + 3(K-1) features behind a flag defaulting
to off, and mark the scheduler legacy in the registry. `state_tracker.py` and `rl_cache_aware_global_scheduler.py`
are in `_VERSION_EXCLUDE`, so this does not touch code_version.

**Hashed file:** no.

### [minor] The leak closure is API-level only: policy code runs in-process and is not screened
`evolve/proposer.py` / `evolve/driver.py` (no import or introspection screen); `load_policy` executes the module in
the simulator process.

**Failure scenario:** an LLM-proposed candidate could `import gc` and read `Request._num_decode_tokens` (or
`_block_hash_ids`) from live objects. The scheduler would never notice, and the score would be oracle-informed.

**Evidence:** no current policy, finalist, probe, design or golden policy does this (grep for `vidur`, `gc`,
`inspect`, `sys.modules`, `_getframe`, `f_back`, `__self__`, `get_referrers`: no hits). There is no static check in
the proposer or driver. This predates v4.1 and is not introduced by this delta.

**Fix:** an AST import allowlist (math, random, statistics, collections, heapq, itertools, functools, numpy) plus a ban
on dunder attribute access, applied in the driver before a candidate is scored and in `head_to_head` for finalists.

**Hashed file:** no.

### [nit] `prompt_block_hashes` raises on a float trace block size
`vidur/scheduler/global_scheduler/prompt_hashes.py:27`.

**Failure scenario:** a trace in which some rows lack `block_hash_ids` gets a float `block_size` column from pandas
(NaN rows). With no `block_tokens` passed (the state-tracker path, or the evolved path without a KV manager),
`hashes[: p // 16.0]` raises `TypeError: slice indices must be integers`.

**Evidence:** repro `Request(0.0, 56, 300, list(range(22)), 16.0)` gives a TypeError with no `block_tokens` and works
with `block_tokens=16`. All three v4 traces have an `int64` block_size column with no NaN, so no current run is
affected.

**Fix:** `bt = int(block_tokens or request.block_size or 0)`.

**Hashed file:** yes (`prompt_hashes.py`). Defer to the next version bump.

## Note (not a finding)
sim_fork forks carry the true decode lengths of in-flight and future requests (`sim_fork.py:631` copies
`_num_decode_tokens`). The headroom headline is a hindsight oracle by design. Any planning router built on sim_fork
(the "RL + planning co-primary" plan) must use the sampled-lengths mode, or its decisions are oracle-informed. v4.1
makes that mode cleaner: router ledgers no longer carry the refitted output ids.
